**2. The route and “read once”**

For one ordinary selection → pre-flight → Create sequence:

| Worker step | Before: detector calls | After: detector calls |
|---|---:|---:|
| Inspection | 0 | 1 |
| Pre-flight | 1 separate call | 1 inside `inspectFile`; no second call |
| Processing | 0 | 1 inside `inspectFile` |
| **Total** | **1** | **3** |

Each additional pre-flight repeats inspection and therefore adds another detector call.

The relevant points are [inspect.ts:349](/Users/uazjob/UoN-Video-Helper-side/vh231/src/media/inspect.ts:349), worker inspection calls at lines 215, 424 and 468, and pre-flight’s reuse at line 551.

Thus:

- **Once per worker step:** yes.
- **Once per complete job:** no.
- **No duplicate detector invocation inside pre-flight:** yes.

The criterion explicitly describes pre-flight’s own inspection consuming this fact, and VH-82 remains open. I therefore accept this as the described per-step route, **not as completion of VH-82 or a single-read job**. The close decision should state the actual counts.

The detector remains bounded: a 1 KB head and tail windows growing through 4, 8, 16 and 32 MiB. These are buffered slices, not a `ReadableStream`; growing windows reread overlapping bytes. A sufficiently small file fits entirely inside a tail slice. This is the existing bounded-window design, not a new unbounded whole-file allocation. It adds no decode pass. Non-Matroska/WebM containers return false before these slice reads.

**3. Other behaviour**

The change has effects beyond the three visible destinations:

- **Every `inspectFile` caller changes.** Acceptance tooling and the framerate, content-class, modes, real, shapes and estimate spikes now perform the detector read for Matroska/WebM too. Intact files incur that work as well as cut files. Other containers acquire the false report field without detector slice I/O.
- **Diagnostics gain a field.** `main.ts:1552` passes the report to `setDiagnosticsContext`, so the dev bundle now includes `source.cutShort`. This is a non-identifying boolean, not a filename or media payload. The production feedback allow-list does not automatically expose it.
- **Read errors propagate.** A detector rejection now fails initial inspection or processing where those steps previously did not perform this read. Worker handlers catch it; they do not silently substitute false. Inspection reports an unreadable-source failure; pre-flight and processing use their existing failure paths.
- **Cancellation is bounded by completion of this operation.** The detector accepts no signal. `inspectFile` checks cancellation after it returns. Cancellation during the read cannot publish a successful report, but does not interrupt its tail-window reads immediately. Worker catch handlers also recognise an aborted signal.
- **The record and finished warning use different snapshots.** `main.ts:3113` captures the selection inspection’s flag, whereas processing supplies the warning from a fresh inspection. Ordinary File/Blob usage keeps this coherent, and choosing another file invalidates the earlier selection. But if successive reads could successfully observe different bytes, the code does not reconcile those flags; a stale record and fresh warning could disagree. An underlying file becoming unreadable instead takes the failure path. The walks do not exercise either case.
- **There is no initial “whole video” flash while inspection is pending.** Selection clears the report and sets the trim’s reading state. The reply assigns `inspectedReport` before `resetTrim` renders the summary (`main.ts:1491–1495,1547–1548`). The cut-aware line is therefore the first populated summary.
