# VH-234 #1 — Claude's design (saved 2026-11-09, before Codex's `design` answer is opened)

Base `73d16f0`; walker `7db38f355f3c46c2`; brief `vh234-1-brief.md` (69f28b93).

## 1. Why VH-205 set `--line-height-heading`
- `git show cc12788` adds `line-height: var(--line-height-heading)` with the 20 px square (`--control-size`), the `::after` target and `inline-flex` centring. Neither the commit body nor the VH-205 entry (`project/decisions-2026-10.md`, 2026-10-27) gives a reason for the line height; the entry's readings are the row (24 px), the square (20 × 20), the hit test and the tip, nothing about the glyph's line.
- Inferred: so the glyph's line box fits inside the square's content box. With `box-sizing: border-box` and a 1 px border, the content box is 18 px at the 16 px root. 14 px × 1.25 = 17.5 px fits, and 14 × 1.5 = 21 px does not; at the 32 px root it is 38 px against 35 or 42. It was a fit, not a role choice. VH-166's "one type set" test counts only `font-size:` declarations (8), so a line height set outside the role passed it.

## 2. The remedy: drop the declaration (chosen), or name the role's token
- **Drop** `line-height: var(--line-height-heading);` from `.promise-with-help .help-button` (`src/styles/app.css:1198`). The compact emphasis role's one rule (`:1868`–`:1874`, `.help-button` in its list, (0,1,0), later in source than `.button`) then gives 0.875rem / 1.5 / 600. `grep -n line-height app.css` shows no other rule naming the "?" with a line height. One line removed, no token, no literal, and no word or element. It is VH-166's form: type comes from the role's one rule, and the component rule sets only the box.
- **Naming `var(--line-height-body)`** there gives the same computed value. But it is a second source of the role's line height outside the role's rule, the drift VH-166 removed. Not chosen.
- **Centring.** The button is `inline-flex; align-items: center; justify-content: center`, with a fixed `height` and `width` (`--control-size`). The anonymous flex item, one line of "?", grows from 17.5 to 21 px (16 px root) and is centred in the 18 px content box. It overflows 1.5 px above and below, which is `align-items: center`'s default, unsafe, centring. Half-leading keeps the glyph's content area centred in its line box, so the glyph's centre does not move. Expected: the same pixels, give or take 1 px of baseline snapping. `.button` sets no `overflow`, so nothing is clipped, and the ink of "?" (about 10 px at 14 px) is well inside the square. Measured, not assumed: the image compare of Part C's 192 shows any pixel moved.
- **The row.** `vertical-align: middle` aligns the box's midpoint, and the box's height is fixed, so the inner line box cannot change the promise's 24 px line. Read by the probe (`rows`) in all 192 states and by S-141's row.
- **Unchanged by construction:** the `::after` target (absolute, centred on the box); the gap (`margin-left: var(--spacing-02)`); the open fill; the tip's `margin-top`. Also `#about-help-button` and `#onset-help-button`, which `.promise-with-help` does not match and which already read 1.5.

## 3. How the walker's `type` resolves a role
- `qualify.mjs` `TYPE_READ`/`typeRoles` (`:932`–`:991`) take each visible text element's computed family (first name), size in rem, weight and line height as a ratio, rounded to 0.01. They match `TYPE_ROLES` with size within 0.01 and line height within 0.02, the line height skipped under `spacing`. The "?" now reads Arial / 0.875rem / 1.25 / 600, no role, a fail. After it reads 1.5, compact emphasis. The 9 spacing cells pass both sides.
