1. **CSS proposal**

   The present `--mark-width 1fr auto` grid lets the value squeeze the label; inherited `overflow-wrap: anywhere` then fragments it. See [app.css:318](/Users/joe/Library/CloudStorage/OneDrive-TheUniversityofNottingham/_Joe%20Bell%20UoN%20Files/2_Projects/2026-08-24%20UoN%20Video%20Helper/src/styles/app.css:318) and `app.css:40`.

   I would retain the existing gutter and use wrapping flex layout, with the mark hanging into that gutter **while remaining in the baseline calculation**:

   ```css
   .system-check .check {
     display: flex;
     flex-wrap: wrap;
     align-items: first baseline;
     min-inline-size: 0;
     padding-inline-start: calc(var(--mark-width) + var(--spacing-04));
   }

   .system-check .check > .mark {
     flex: none;
     inline-size: var(--mark-width);
     margin-inline-start:
       calc(-1 * (var(--mark-width) + var(--spacing-04)));
   }

   .system-check .check > :not(.mark) {
     min-inline-size: 0;
     max-inline-size: 100%;
   }

   .system-check .check > :nth-child(2) {
     flex: 1 1 max-content;
   }

   .system-check .check > .value {
     flex: 0 1 max-content;
     text-align: start;
   }
   ```

   Existing gap, borders, typography, colours and `overflow-wrap` remain. The label grows into spare space; the value wraps when their natural one-line widths plus the gap exceed the text area. The `100%` cap lets an oversized label occupy that area without leaving the mark alone on a previous flex line.

   **Content-driven, not a viewport or container breakpoint:** available space, translation, actual font and spacing determine the transition. A width query cannot detect those content differences.

   Failure modes to test explicitly:

   - At 320 px and a 32 px font, a Malay word such as **Pemprosesan** may exceed even the freed text column. Emergency wrapping must still work; “every word always whole” is incompatible with that constraint.
   - Spacing increases intrinsic widths and produces earlier stacking and taller rows.
   - The existing narrow mark gutter can wrap Malay **Tidak** or Chinese marks. Count and inspect that too; first-baseline alignment does not guarantee a one-line mark.
   - Removing the size cap risks an orphaned mark; using an absolute-positioned mark risks incorrect baseline placement. This proposal avoids both.

2. **Value placement and alignment**

   Beneath: start at the **label’s inline-start edge**, below its last line—not beneath the mark or against the row’s far edge. Beside: occupy the row’s inline end, sharing the label’s first baseline. Use `text-align: start` throughout; do not add an auto start margin that would also right-align a stacked value.

   WCAG 1.4.8 forbids full justification; it does **not** itself forbid right alignment. Start alignment is my readability choice for these verbal outcomes, especially the long AAC warning. Preserve the measure, line spacing, user colours and enlargement behaviour too. 6. **Honest line and word measurements**

   Measure **mark, label and value separately**, plus the row’s occupied visual lines. Retain each line’s text and geometry. Do not divide row height by line height: padding, gaps and different type sizes make that wrong.

   The walker’s `renderedLines` is useful, but its whole-`li` reading joins adjacent children geometrically. That can concatenate mark, label and value into a fictitious “word” (`qualify.mjs:246–284,311–314`). Add the component-level reader in the external driver.

   Record:

   - Longest source word/token: text, grapheme count and unwrapped rendered width.
   - Its actual line fragments, and **every word split**, not merely the longest surviving fragment.
   - The available text-column width, so necessary emergency breaks are distinguishable from avoidable squeezing.

   Chinese is not one enormous word because it lacks spaces. Count graphemes and retain normal Chinese line-break opportunities; linguistic word segmentation is descriptive, not a prohibition on ordinary CJK wrapping. Inspect embedded Latin tokens such as **WebCodecs** separately. For 1.4.8, retain the walker’s CJK/mixed-script readings and its uncertainties; the house measure counts CJK glyphs as two (`UI-STANDARDS.md:209–211`).
